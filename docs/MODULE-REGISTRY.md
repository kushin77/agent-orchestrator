# Module registry — one honest view of every module

Status: **published and gated** (2026-09-14). Lane: issue #445 (parent #422);
control-plane evidence for the surface added by issue #591 (§8).
The machine-readable register this document describes is generated by
[`../governance/modules/`](../governance/modules/README.md); the gate that
enforces it is [`../scripts/check-module-registry.sh`](../scripts/check-module-registry.sh).

This is the missing middle between the hub's "**what ships where**" — the GR-18
mandatory flags in `catalog/modules/<id>/module.json`, the `catalog/mandatory.tsv`
registry, `catalog/validate.py` and the seeds under `templates/module/` — and this
repo's **consumers of that truth**: the PMO rollup (#403), the paperclip HTTP
projection (#413) and peer-board triage (#427). Nothing else in this repository
answers *"what is the module set, what is mandatory, what is pending, and what is
drifting?"* in one place. `kushin77/CMR#952` says the same at the hub: portfolio
membership and module membership are not the same set, and they have drifted.

The registry is a **view**, not a store. It writes nothing: it reads the hub, this
repo's declared targets and this repo's admission register, and reports.

## 1. What is read (in precedence order)

| # | Surface | Role |
|---|---------|------|
| 1 | the pinned hub submodule `vendor/CMR`: `catalog/mandatory.tsv` + `catalog/modules/*/module.json` | **the authority** on membership and mandatory status |
| 2 | [`governance/modules/targets.json`](../governance/modules/targets.json) | what the mandatory set *should* become — each target naming the blocking hub issue(s) |
| 3 | the root [`module.json`](../module.json) `submodules` register | this repo's admission **claims**, which never confer membership |
| 4 | the in-tree vendoring scan | proof that 1–3 are references, not copies |

The hub is **read-only** in this repository: it is the pinned submodule. Drift
between its two surfaces — the flags and the registry — is refused in *either*
direction, mirroring the hub's own `catalog/validate.py` (GR-18).

## 2. Three states, never two — plus a refusal that is not a state

| State | Meaning | `shipped` |
|---|---|---|
| `registered-mandatory` | in the hub catalog with `mandatory: true`, with a `mandatory.tsv` row in lockstep | `true` |
| `target-pending` | declared in `targets.json`, not yet in the hub catalog | **`false`** |
| `catalog-module-not-mandatory` | in the hub catalog, outside the mandatory set | `true` |

A module in the target set that is not yet registered is **never** reported as
shipped: `target-pending` carries `shipped: false` and the blocking hub issue(s)
by name, because an unnamed blocker is a wish rather than a target. This is the
honest two-part-surface discipline the hub requires for a `Pending` row.

`not-a-module` is deliberately **not** a fourth state. It is the refusal the
membership query returns for any name the hub catalog does not carry — reported
**by name**, in its own list, counted separately, and never folded into the module
list. That is the `kushin77/CMR#952` drift guard: *a finding about a non-module is
not membership*.

## 3. Membership is refused, not inferred

A claim never confers membership:

```bash
$ python3 governance/modules/cli.py membership hermes-agents
not-a-module: hermes-agents — the hub catalog carries no module with this id — portfolio
membership is not module membership (kushin77/CMR#952); the local admission register
records admission='requested', which does not confer membership
  claim   admission='requested' request='kushin77/hermes-agents#3' — a claim is not membership
```

The register may say `admission: "declared"`; the answer is still `not-a-module`,
and the detail says why. The catalog is the only source of membership.

## 4. No vendoring — the registry stores references

Every module entry records a **reference** — `id`, `repo`, `pin`, `path` — and the
path is hub-relative (`catalog/modules/<id>/module.json`). The only vendor path in
this repository stays `vendor/CMR`. A gate finding fires, by name, when a module's
*source* is carried in-tree instead of referenced:

- `VENDOR-SOURCE-IN-TREE` — a hub module's `module.json` copied into this tree, or
  a submodule vendoring a module directly;
- `VENDOR-IN-TREE-PACKAGE` — a module's declared distribution package present
  in-tree (`codeidx/`, `node_modules/@kushin77/saas-rbac`);
- `VENDOR-EXTRA-SUBMODULE` — any vendored submodule path other than `vendor/CMR`;
- `VENDOR-PATH-OUTSIDE-HUB` — a registry reference that resolves outside the hub.

## 5. Deterministic and mutation-proven

Two builds over one revision are **byte-identical**: every list is sorted, keys are
sorted, no field records when it was read, and the hub root is recorded as given
(`vendor/CMR`, never absolutised) so the document travels between checkouts.

The gate provokes each acceptance refusal in a **scratch copy** of the hub or of a
consumer tree — never in the lane tree and never in the read-only submodule — and
requires each one to be refused **by name**. A check whose pass and fail paths
collapse into the same exit code is a formality (AO-GR-4 / GR-12):

| Provoked | Refused by name |
|---|---|
| a duplicated module id | `MODULE-DUPLICATE-ID: shared-frontend` |
| a mandatory consumer asset with no seed | `MODULE-ASSET-NO-SEED: shared-frontend` |
| unregistered-but-mandatory, registry surface | `MODULE-UNREGISTERED-MANDATORY: ghost-module` |
| unregistered-but-mandatory, flags surface | `MODULE-UNREGISTERED-FLAG: erp-crm` |
| a declared target that landed unregistered | `MODULE-TARGET-LANDED-NOT-MANDATORY: pmo` |
| a hub manifest copied in-tree | `VENDOR-SOURCE-IN-TREE: shared-frontend` |
| a distribution package carried in-tree | `VENDOR-IN-TREE-PACKAGE: codeidx` |
| an extra vendored submodule path | `VENDOR-EXTRA-SUBMODULE: third_party/hermes` |
| a reference pointing outside the hub | `VENDOR-PATH-OUTSIDE-HUB:` |
| membership claimed for an unknown name | `not-a-module: not-a-module-anywhere` |
| a policy that files a refusal code as `recorded` | `MODULE-DUPLICATE-ID` named, `recorded` refused |
| a policy that does not declare a code the registry emits | the undeclared code, named |
| a policy that would let a claim confer membership | `membership-not-inferred-from-a-claim` |
| a schema the emitted document cannot satisfy | the violating document path, named |
| a trail of another shape appended to | that trail's schema tag, named |

A clean scratch tree is asserted to be refused **nothing**, so the vendoring check
cannot be always-red, and the hub root is also asserted to *flip*: a target that
lands in the scratch catalog is derived as `registered-mandatory` rather than
staying `target-pending`.

## 7. The gate

`bash scripts/check-module-registry.sh` — exit-code contract **0 OK / 1 NOT-OK /
2 CANNOT-ASSESS**. CANNOT-ASSESS is never a pass: a clean clone has no submodule,
so there is no authority to read, and the gate says so (and proves that path by
provoking an empty hub). It requires the registry to be clean, deterministic,
reconciled with both hub surfaces, honest about every acceptance field, and to
refuse every provoked mutation by name.

It also drives the three artifacts of §8 through the CLI, never by editing this
tree: a policy mutant that files a refusal as `recorded`, a policy mutant with an
undeclared code, a policy mutant whose authority would let a claim confer
membership, a schema mutant the emitted document violates, and a trail of another
shape — each must be refused **by name**, and the clean run must stay green. A
registry whose policy, schema or trail could be ignored would satisfy every other
check in this gate while judging nothing.

Wiring the gate into `make verify` is the orchestrator's step (a new
`scripts/check-*.sh` is inert until `scripts/verify.sh` names it, and
`gate-coverage` fails until then — the expected state for a new lane).

## 8. The three artifacts that judge a build (issue #591)

The registry's row shape was implicit in `registry.py` and promised only in prose;
which conditions are fatal lived in code. Three declared artifacts now judge every
build, and each one is **read by the code path** rather than described next to it:

| Artifact | What it declares | How the code uses it |
|---|---|---|
| `governance/modules/controls.yaml` | the acceptance policy: which conditions are **fatal** (hub drift, a registered module whose consumer asset has no seed, a duplicated module id, module source carried in-tree, membership inferred from a claim) and which are **recorded** (the judged states, and a membership refused by name) | `policy.py` is read on every build; `registry.build` **stamps every refusal** with the declared condition and disposition, and a code the policy does not declare is CANNOT-ASSESS — never an unjudged refusal travelling as evidence |
| `governance/modules/module-registry.schema.json` | the frozen document and row shape, closed (`additionalProperties: false`), with the refusal-code vocabulary as an enum | `schema.py` (a stdlib-only subset validator) is enforced **on the document the generator is about to return**, so a malformed row never leaves `registry.build`; the violation names its JSON path |
| `governance/modules/audit.py` | the append-only trail of every refusal and every judged name, one record per judgment | `registry.build` projects the judged document into the records it carries; `cli.py verify --audit FILE` **appends** them and proves the file grew rather than changed (the bytes read first must be an exact prefix) |

The dispositions are not hard-coded a second time: the trail says what
`controls.yaml` declared, and `verify`'s exit code follows the disposition the
document carries. A refusal is **always** fatal — `policy.load` refuses a policy
that files a refusal code under `recorded`, because a gate that can be turned off
by editing a YAML file is a gate that cannot fail (AO-GR-4 / GR-12). A policy that
would let a claim confer membership is refused as a policy that weakens the guard,
which is the `kushin77/CMR#952` drift guard itself.

Control-plane evidence this surface now shows
(`governance/conformance/surfaces.py::measure_path_evidence`, measured on this
lane's tree):

```
{'contract': True, 'tests': True, 'controls': True, 'audit': True, 'schema': True, 'live_sync': False}
```

`controls`, `audit` and `schema` were the three this surface was missing; raising
its declared class is a change to `governance/conformance/surfaces.yaml`, which
this lane does not own.

## 10. Boundary (NG4)

This lane reads the hub and this repository; it writes into neither. A need that
lands on the hub or on a peer is a **direction issue on that board**. Membership is
declared by the authority; this registry only reports what it finds.
